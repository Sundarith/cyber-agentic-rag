\section{Introduction}

Mapping newly disclosed Common Vulnerabilities and Exposures (CVE) records to root-cause Common Weakness Enumeration (CWE) identifiers is a recurring task in cyber threat intelligence (CTI). The mapping determines how analysts group vulnerabilities, select mitigations, prioritize remediation, and connect newly disclosed flaws to existing weakness taxonomies. Errors in this step propagate into downstream analysis, so CVE-to-CWE mapping is a narrow but important target for automation.

Large proprietary language models can perform this mapping when given only the CVE description, but their use introduces deployment costs: paid API access, transmission of vulnerability data to a third party, and limited reproducibility. Security-specialized open models have narrowed the gap, reaching up to 75.6\% on the CTI-Bench RCM benchmark \cite{mosievskiy-2026}, yet still fall short of closed security systems reporting around 85--86\% \cite{google-2025a,google-2025b}. For reference, GPT-4---the published no-retrieval frontier anchor for this benchmark---scores 72.0\% \cite{alam-2024}. Local 7B--8B models without retrieval augmentation remain substantially weaker still.

This paper studies whether local 8B-class models can close that gap by reading public vulnerability knowledge at inference time. We build a graph-augmented hybrid retrieval-augmented generation (RAG) pipeline over two public sources: the National Vulnerability Database (NVD) CVE corpus and the official MITRE CWE corpus. The pipeline combines BM25 and dense retrieval, explicit CVE-to-CWE bridge injection, weighted nearest-neighbor voting, cross-encoder reranking, and HyDE candidate expansion with cross-encoder filtering. We then add a deterministic model router: NVD-mapped CVEs are sent to a RAG-specialized model, while NVD-unmapped CVEs are sent to a security reasoning model.

The central research question is: under the CTI-Bench single-answer protocol, how far can local open-source 8B-class models go when paired with a retrieval pipeline over public CVE and CWE data, and which retrieval stages contribute most to the final accuracy?

This work makes four contributions:
\begin{itemize}
\item We present a two-source graph-augmented hybrid RAG architecture for CVE-to-CWE root-cause mapping using only public NVD and CWE data.
\item We introduce a mapped/unmapped execution split: an NVD bridge fast path for mapped CVEs and a multi-stage reasoning path for unmapped CVEs.
\item We evaluate the pipeline on all 1,000 CTI-Bench RCM queries and report ablations for phrase selection, cross-encoder reranking, HyDE filtering, and k-NN confidence calibration.
\item We show that a deterministic routed ensemble reaches 86.4\% strict accuracy, surpassing the strongest published open-source specialist by 10.8 percentage points and exceeding GPT-4, the published no-retrieval CTI-Bench anchor, by 14.4 percentage points---all while running locally on commodity hardware.
\end{itemize}

\section{Background and Related Work}

Prior work on automated CVE-to-CWE classification and RAG-based security analytics falls into three lines: general retrieval and reranking foundations, CVE-to-CWE classification methods, and security-tuned LLMs. We review each in turn.

\subsection{Retrieval-Augmented Generation}

Retrieval-Augmented Generation (RAG) combines a parametric generator with non-parametric retrieval over an external corpus \cite{lewis-2020}. This decoupling is central to our design: instead of fine-tuning the language model to memorize the CWE taxonomy, we expose authoritative CWE and CVE evidence at inference time. BM25 remains a strong sparse retrieval baseline for exact identifiers and rare terms \cite{robertson-2009}, while dense bi-encoders such as Sentence-BERT and BGE capture semantic similarity \cite{reimers-2019,xiao-2024}. Prior ranking work motivates combining sparse and dense signals and reranking with a cross-encoder \cite{lin-2021,nogueira-2019}. We use this two-stage pattern to discriminate fine-grained CWE candidates whose definitions share most vocabulary.

HyDE retrieves against a generated hypothetical answer rather than the original query \cite{gao-2022}. In our setting, the hypothesis is a short CWE-style weakness description produced from CVE prose. Because generated hypotheses can introduce noise, we score HyDE candidates against the original CVE description with a cross-encoder before adding them to context.

\subsection{CVE-to-CWE Classification}

CTI-Bench provides the evaluation protocol used in this paper: 1,000 CVE descriptions with manually curated CWE labels, evaluated by strict identifier match under a single-call LLM protocol \cite{alam-2024}. ThreatZoom introduced an early neural CVE-to-CWE classifier using hierarchical CWE structure \cite{aghaei-2020}. More recently, Mosievskiy fine-tuned RoBERTa-base on CVE-to-CWE pairs and reported 75.6\% strict accuracy on CTI-Bench RCM \cite{mosievskiy-2026}. Our approach differs from these classifiers by retrieving public CVE/CWE evidence at inference time rather than relying only on the CVE description.

Cybersecurity instruction tuning alone has not closed the gap on CTI-RCM. CyberPal.AI reports a best CTI-RCM score of 60.65\% after full-parameter cybersecurity SFT \cite{levi-2024}. AttackQA, though focused on ATT\&CK question answering rather than CVE-to-CWE mapping, found that tuning the retrieval model contributed more than tuning the generator \cite{krishna-2024}. These results support a retrieval-first approach.

\subsection{Security LLMs and Routed Models}

Security-tuned LLMs provide important comparison points. Cisco's Foundation-Sec models continue pre-training and reasoning tuning on cybersecurity corpora \cite{kassianik-2025,yang-2026}. Trend Micro's Llama-Primus and WhiteRabbitNeo pursue similar cybersecurity adaptation \cite{yu-2025,whiterabbitneo-2024}. Closed systems such as Sec-Gemini and SecLM report strong CTI-RCM results but are not locally reproducible \cite{google-2025a,google-2025b}. IBM Granite 4.1 8B emphasizes RAG and tool-use behavior in its training mix \cite{ibm-granite-2026}.

The routed ensemble in this paper is motivated by evidence that RAG-oriented fine-tuning can trade off grounded extraction against general reasoning. Huang et al.~\cite{huang-2025} document catastrophic forgetting under RAG fine-tuning on Qwen2.5-7B-Instruct; Mallen et al.~\cite{mallen-2022} show that retrieval and parametric memory dominate in different regimes. We use public NVD mapping status as a deterministic routing signal: mapped CVEs are cases where retrieval has an authoritative answer, while unmapped CVEs require more abstractive CWE reasoning.

\section{Graph-Augmented Hybrid RAG}

\subsection{Knowledge Base}

The knowledge base contains two sources. First, the official CWE XML corpus is chunked into weakness entries containing identifiers, names, descriptions, alternate terms, hierarchy information, and related explanatory text. Second, NVD CVE records are chunked from CNA and ADP containers. Structured NVD CWE assignments are extracted from the official NVD weakness fields. Textual mentions of CWE identifiers inside CVE prose are not treated as graph edges; only structured NVD fields are used for CVE-to-CWE bridges.

This produces approximately 332,000 chunks, including roughly 150,000 CVE records with structured CWE assignments. Each chunk has a sparse BM25 representation and a dense BGE-small embedding. A lightweight CVE-to-CWE index records whether each CVE has an NVD CWE mapping and is used both for bridge injection and for runtime routing.

\subsection{Retrieval Pipeline}

Given a CTI-Bench prompt, the system performs hybrid retrieval with equal BM25 and dense weights. The initial top-$K$ pool uses $K=8$. If the retrieved CVE chunk carries a structured NVD CWE assignment, the pipeline takes a fast path: the bridge-mapped CWE chunks are injected into context, competing CWE chunks are removed, and the final prompt is assembled without HyDE, k-NN fallback, or cross-encoder reranking.

If no structured bridge fires, the pipeline follows the unmapped reasoning path. HyDE first generates a short hypothetical weakness description from the CVE prose, retrieves additional CWE candidates against that hypothesis, and filters them with a BGE-Reranker-Base cross-encoder against the original prompt. The system then computes weighted votes from the five nearest mapped CVE neighbors. A vote is treated as authoritative only when its weighted share is at least 0.90 and its margin over the runner-up is at least 1.50; otherwise it remains a soft hint. Finally, all remaining CWE candidates are reranked with the cross-encoder before context assembly.

Figure~\ref{fig:pipeline} summarizes the two execution paths. Mapped CVEs follow a short evidence-injection path, while unmapped CVEs use candidate expansion, nearest-neighbor evidence, and reranking before the final answer call.

\subsection{Routed LLM Ensemble}

The final answer model is selected by public NVD mapping status. NVD-mapped CVEs are assigned to IBM Granite 4.1 8B, which is optimized for grounded RAG-style response behavior. NVD-unmapped CVEs are assigned to Cisco Foundation-Sec-8B-Reasoning, which is used as a specialist for taxonomy-reasoning cases where no authoritative NVD bridge is available. The routing decision is deterministic and depends only on metadata available before inference.

This routing rule does not inspect CTI-Bench labels. It uses the same NVD mapping status that would be available for a newly disclosed CVE. The rule is nevertheless a limitation: its direction was selected after observing subset-specific behavior on this benchmark, so future validation on new splits is needed.

\section{Experimental Setup}

\subsection{Benchmark and Metrics}

We evaluate on the CTI-Bench CTI-RCM split \cite{alam-2024}. The benchmark contains 1,000 CVE-to-CWE prompts and ground-truth CWE identifiers. We use each row's \texttt{Prompt} field directly and score by strict CWE identifier match. The benchmark divides naturally into 903 NVD-mapped CVEs and 97 NVD-unmapped CVEs according to the local NVD index.

\subsection{Models}

The single-model locked recipe uses Qwen2.5-7B-Instruct as the final answer model. Additional probes include Qwen3-8B, IBM Granite 4.1 8B, and Foundation-Sec-8B-Reasoning. The routed ensemble uses Granite for NVD-mapped final calls and Foundation-Sec for NVD-unmapped final calls. Retrieval-side components use BM25, BGE-small embeddings, and a BGE cross-encoder reranker; the final-answer models are not fine-tuned.

\subsection{Protocol}

The evaluation preserves the CTI-Bench final-answer protocol: one final LLM answer call per query at the configured default decoding settings. Retrieval-side HyDE calls are not final answer calls; they generate only hypothetical weakness text for candidate expansion. We report full-benchmark accuracy, mapped and unmapped subset accuracy, ablations of retrieval stages, and wall-clock runtime as a secondary engineering measure.

\subsection{Reproducibility Controls}

To preserve comparability with CTI-Bench, we use the benchmark prompt text unchanged and score only strict CWE identifier matches. Each reported condition is evaluated on the full 1,000-query split. Retrieval uses only public NVD and CWE sources, and CVE-to-CWE graph edges are constructed only from structured NVD weakness fields rather than textual CWE mentions in CVE prose. The final-answer models are used without fine-tuning; ablations change retrieval components while holding the benchmark prompts, scoring script, and final-answer protocol fixed.

All experiments run on a single workstation with two NVIDIA RTX 4090 GPUs (24~GB each), serving Granite 4.1 8B (port 8001) and Foundation-Sec-8B-Reasoning (port 8000) via vLLM 0.19.1 with prefix caching. Retrieval-side components (BGE-small bi-encoder, BGE-Reranker-Base cross-encoder, BM25 index) run on CPU. The full 1,000-query routed evaluation completes in approximately 19 minutes with three worker processes. Exact model identifiers, prompts, hyperparameters, and the evaluation harness are released with the paper; verbatim prompt templates are provided in Appendix~A.

\subsection{Data-Leakage Considerations}
\label{sec:leakage}

We separately address two leakage concerns. First, retrieval contents: the retriever indexes 1{,}450 public CWE entries from the official MITRE corpus and approximately 150{,}000 historical NVD CVE records. CWE entries themselves do not contain CVE-to-CWE labels, so retrieving a CWE description cannot expose the CTI-Bench gold mapping. The CVE corpus does carry NVD's own structured CWE assignment, which is the signal the bridge fast path uses; however, on 94/136 routed-run failures (Section~\ref{sec:failure-typology}) the CTI-Bench gold label disagrees with NVD's assignment, and our system follows NVD's structured field rather than the CTI-Bench label. The published-bridge fast path therefore does not ``leak'' CTI-Bench gold answers; it provides whatever NVD curators recorded at disclosure time. Second, language-model pre-training: Foundation-Sec-8B-Reasoning and Granite 4.1 8B were trained before this work and may have seen public CVE descriptions during pre-training; CTI-Bench was published in 2024 \cite{alam-2024}, and prior CTI-Bench papers report the same risk for GPT-4 and Llama-3 baselines. We do not fine-tune the final-answer models on any CTI-Bench data and follow the published single-call protocol unchanged.

\subsection{Routed Ensemble}

Table~\ref{tab:final-results} reports two retrieval-only baselines that skip the LLM entirely and three LLM-augmented configurations. Pure hybrid retrieval (BM25 + BGE) followed by selecting the highest-ranked CWE chunk reaches only 33.2\%, confirming that surface-level lexical or dense similarity is insufficient on its own. Adding the structured NVD bridge for mapped CVEs---still without any LLM call---raises mapped accuracy to 87.8\%, almost identical to the routed system's 87.7\% mapped accuracy. This indicates that the LLM contributes essentially no additional mapped-CVE accuracy beyond the public NVD structured field, and the mapped-subset gains we report are best understood as ``structured retrieval as lookup'' rather than reasoning. On the 97 NVD-unmapped CVEs, retrieval-only stays at 27.8\%; the LLM-augmented pipeline raises this to 72--74\%, accounting for almost all of the LLM's measurable contribution.

Among LLM-augmented configurations, replacing Qwen2.5-7B with Qwen3-8B improves the single-model recipe from 85.1\% to 85.6\%, and the routed Granite/Foundation-Sec ensemble reaches 86.4\%. A Foundation-Sec-only single-model configuration evaluated over two full-benchmark runs reaches 87.4 $\pm$ 0.14\%. A McNemar paired-prediction test between the routed configuration and Foundation-Sec-only (Section~\ref{sec:latency}) gives $p = 0.082$, indicating the two configurations are statistically indistinguishable on this benchmark; we therefore report them as two near-equivalent operating points rather than a single dominant system.

\subsection{Runtime and Latency}
\label{sec:latency}

\section{Discussion and Limitations}

\subsection{Two Regimes: Retrieval-as-Lookup vs.\ Retrieval-plus-Reasoning}

The retrieval-only baselines in Table~\ref{tab:final-results} reveal that the system operates in two distinct accuracy regimes. On the 903 NVD-mapped CVEs, the LLM-free hybrid + NVD bridge configuration reaches 87.8\%, statistically indistinguishable from the full routed pipeline's 87.7\%. The mapped-subset contribution is therefore best characterized as ``retrieval-as-lookup'': public structured NVD evidence resolves the question, and the LLM serves to format the answer rather than reason about it. On the 97 NVD-unmapped CVEs, retrieval-only stays at 27.8\% and the LLM-augmented pipeline lifts this to 71--74\%, accounting for a 43--46 percentage-point gap that is entirely attributable to the LLM and the retrieval refinements (HyDE, k-NN voting, cross-encoder reranking) feeding it. The ablation table corroborates this split: retrieval-side reordering improves unmapped accuracy from 61/97 to 72/97, while prompt-heavy and override-heavy mechanisms tested during development did not provide stable gains.

\subsection{Why Routing Helps}

The mapped and unmapped subsets stress different model behaviors. Mapped CVEs are primarily grounded extraction problems: the system finds the matching CVE chunk and injects NVD's structured CWE assignment. Granite is well suited to this path because it is optimized for RAG-like grounded response behavior. Unmapped CVEs lack an authoritative bridge and require a taxonomic classification decision from prose; Foundation-Sec and Qwen3 are stronger on that reasoning-heavy subset. This is consistent with prior work on RAG fine-tuning and the distinction between retrieval-backed and parametric-memory-backed answers \cite{huang-2025,mallen-2022}.

\subsection{Validity and Limitations}

The comparison to GPT-4 should be interpreted as a deployment comparison, not a raw model-capability comparison. GPT-4 in CTI-Bench had no retrieval over NVD or CWE, while our system has access to public data that analysts normally use. The mapped subset is therefore partly RAG-as-lookup. The unmapped subset is the stricter reasoning test, where the system achieves 74.2\%.

The routing rule is deterministic and uses only public NVD mapping status, but the decision to send mapped CVEs to Granite and unmapped CVEs to Foundation-Sec was selected after observing subset-specific model behavior on this benchmark. A future CTI-Bench split or a held-out CVE set is needed to validate the router without this post-hoc element. Finally, the corpus is intentionally restricted to CVE and CWE sources for CTI-RCM; broader CTI tasks may require adding ATT\&CK, CAPEC, and other threat-intelligence sources.

This work uses only public NVD CVE records, public CWE definitions, and public benchmark prompts. It does not generate exploit code, disclose previously unknown vulnerabilities, or involve human subjects. Outputs should be treated as analyst decision-support recommendations, not authoritative vulnerability assignments, since incorrect CWE mappings can misdirect remediation.

\subsection{Non-Adopted Alternatives}

Several plausible alternatives regressed. T-RAFT LLM fine-tuning on CVE-to-CWE examples reduced full-benchmark accuracy by roughly nine cases, largely because the model emitted verbose reasoning preambles where terse CWE answers had previously succeeded. BGE-small contrastive fine-tuning regressed by 29 cases because it shifted embeddings away from CVE self-retrieval and used false-negative hard negatives. A cross-encoder LoRA attempt also regressed after filtering out many of the hardest examples. Larger cross-encoders and self-consistency did not provide comparable, protocol-preserving gains.

\subsection{Future Work}
\label{sec:future-work}

Four directions address the remaining failure modes. (1)~Domain-adapted retrieval: a cross-encoder fine-tuning recipe with stronger false-negative filtering \cite{moreira-2024} may reduce context misses, which account for approximately 60\% of residual failures. (2)~Catastrophic-forgetting-aware fine-tuning: distillation-based RAG fine-tuning \cite{huang-2025} may improve near-miss failures without regressing easy cases. (3)~Confidence-weighted routing: replacing the binary NVD-status router with a continuous signal combining bridge strength, k-NN margin, and cross-encoder score gap may improve borderline cases. (4)~Generalization: the same two-source architecture should be evaluated on other CTI-Bench tasks to test whether the retrieval design extends beyond root-cause mapping.

\section{Conclusion}

This paper presented a Graph-Augmented Hybrid RAG system for CVE-to-CWE root-cause mapping. Using only public NVD and CWE data, the routed Granite/Foundation-Sec ensemble reaches 86.4\% strict accuracy on CTI-Bench RCM. The result exceeds the published GPT-4 no-retrieval baseline and the strongest open-source published baseline while remaining local and reproducible.

The main lesson is that careful retrieval design can make small local models competitive on a cybersecurity taxonomy task. Bridge injection solves many NVD-mapped cases, while phrase selection, cross-encoder reranking, HyDE filtering, and calibrated k-NN voting improve the harder unmapped cases. Routing adds a final gain by matching model behavior to the mapped/unmapped structure of the task.
